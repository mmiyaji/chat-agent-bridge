# アプリ更新時のデータ移行

データ形式の変更は `ApplicationDataMigrations.Create()` に登録します。起動するウィンドウや個別の設定画面に移行処理を書かず、Core の `IDataMigration` を実装してください。

## 移行の追加

各処理は次の契約を持ちます。

- `Id`：永続的な識別子。小文字英数字・ドット・ハイフンで64文字以内。
- `Version`：正の整数。既存処理の更新では増やします。
- `IsRequiredAsync`：現在のデータから実行が必要か判定します。
- `ExecuteAsync`：移行を実行します。途中で止まっても再実行できるようにします。
- `ValidateAsync`：移行先の完全性を検証します。入力元が既に消えていても、未記録の移行先を検証できる必要があります。

依存する処理は登録順に並べます。次の処理の必要性は、前の処理の完了後に判定されます。処理ごとに検証を通過してから `data-migrations.json` にID・バージョン・完了日時を原子的に記録します。処理途中、検証失敗、台帳保存前の終了では完了扱いにしません。

利用者が複数バージョンを飛ばして更新する場合もあります。各処理は台帳の直前バージョンだけを前提にせず、対応する旧データ形式を調べて現形式まで移行してください。

移行処理には、元データを保持したまま一時ファイルへ書き出し、保存内容を検証し、最後に切り替える実装が必要です。共通基盤だけで任意のデータ変更をロールバックできるわけではありません。ファイルの所有範囲、読み込み上限、再解析ポイントの拒否も各処理で守ってください。

## 再起動と古いアプリ

完了済みでも必要性は確認します。古いバックアップを戻した場合にも再移行できます。移行が実行済みなのに完了記録だけがない場合は、検証して記録を補います。

完了した定義は登録から削除しないでください。廃止する処理も、現形式の検証ができる定義を残します。台帳に未知のID、対応版より新しいバージョン、不正な内容があれば起動を止めます。自動の逆移行はありません。旧バイナリへの差し戻しは、対応するデータのバックアップと合わせて判断してください。

## 起動UIと排他

移行と必要な検証はワーカースレッドで実行します。処理が必要な場合や確認に時間がかかる場合は、起動画面に進行表示を出します。正確な割合が分からないため、リングと処理数を表示します。

正常終了するまで通常ページを構築せず、自動接続・添付回収・価格更新・更新確認・保持期限処理は起動ゲートを待ちます。言語・テーマなど起動画面に必要な設定と、起動診断の記録は先に利用します。失敗時は再試行と終了だけを提示し、通常運用を始めません。

共通基盤は同一プロセス・同一データフォルダーの処理を直列化します。プロセス間排他はアプリの `SingleInstanceGate` が前提です。別のツールから使用する場合も同等の排他が必要です。

## 現在の移行と検証

初回の登録は `audit-jsonl` バージョン1です。旧 `audit.json` をJSONLの分割ログへ移行します。元ファイルを削除する前に、決定的な分割結果と保存された全バイトが一致することを検証します。

Coreの `DataMigrationTests` と `AuditStoreTests` で、中断・再試行・依存順・検証失敗・不正台帳・新しい版の拒否を検証します。実機の起動失敗、再試行、再起動、終了は `desktop/DataMigrationStartupUiSmoke.ps1` で隔離データを使って検証できます。

# Durable activity statistics

Execution history remains a rolling list of at most 500 records in `history.json`. Activity and usage charts read a separate `activity-statistics.json` aggregate so totals continue to include older executions after that list evicts them.

The statistics document stores calendar-day totals, status totals, model counts, usage counter aggregates, and bounded cost-feature aggregates. It stores no prompts, output, channel, thread, user, workspace, or session fields. It retains at most 3,660 calendar days, 128 activity model buckets per day, 1,536 usage groups per day, and 1,024 cost-feature shapes per usage group. Excess model labels are folded into a localized “other models” bucket. It keeps at most 500 recent finalized execution IDs to make retries idempotent and at most 500 active IDs so long-running executions can complete safely. It never evicts an active marker to make room; hitting that limit fails the write with a recoverable error. When finalized markers expire, the store advances a start-time cutoff, and replays at or before that cutoff are ignored.

On first use, including the first statistics read, the store atomically seeds aggregates from the retained history currently available. A process interruption before the atomic replacement leaves migration retryable. This migration cannot restore data already evicted before the aggregate store existed. Normal writes update the aggregate file atomically before `history.json`; a retry after a history write failure is deduplicated. Running records are tracked separately and become a finalized aggregate when they finish. On restart, stale running markers are converted to interrupted activity when history is read; orphan markers from a partial history write are also reconciled.

Day assignment uses the machine-local timezone at the time the execution is recorded, converting the instant before extracting the local calendar date. Migration uses the machine-local timezone on migration day. The timezone ID is stored for provenance. Existing day buckets cannot be remapped after a timezone change because the aggregate intentionally does not retain per-execution timestamps.

`ActivityStatisticsStore.ClearAsync` clears aggregate values and writes a completed-migration marker. This prevents a later read from restoring the old values from still-retained history. Data reset should clear both the aggregate store and the execution history through the data-management flow.

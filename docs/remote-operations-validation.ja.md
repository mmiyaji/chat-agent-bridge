# リモート操作の拡充（2026-10-19、未公開）

## 実装と検証の順序

1. Windows承認通知の不達調査。
2. Slack・Mattermostの自動再接続。
3. チャットからの停止・状態確認。
4. Codex App Serverの途中質問へのチャット回答。

各段階でテストとローカルコミットを行う。push・GitHub Releaseへのアップロードは行わない。

## Windows通知：原因未特定のため保留

このPCのポータブル版は通知登録に成功している。初回承認待ちでは通知APIを呼び、送信エラーや通知IDが0の場合は通知欄へ失敗を表示する。IDが発行されても、Windowsがバナーを表示したことまでは確認できない。通知登録用の公式ランタイムDLLは既に配布対象に含まれている。

このPCでは新しい不達原因を再現できず、利用者の指示に従って別PCでの調査を待つ。推測による通知実装の変更は行わない。別PCでは次を記録する。トークン、プロンプト、秘密入力は不要。

- 「情報」のバージョンとWindowsのバージョン・ビルド。
- 起動直後、および新規スレッドの初回承認待ち直後の「チャット受信」の通知欄。
- 管理者として起動しているか。通知バナーがなくても通知センターに届いているか。
- Windows全体・アプリ個別の通知設定と、応答不可の状態。

Microsoftの[通知の案内](https://learn.microsoft.com/windows/apps/develop/notifications/app-notifications/)と[非パッケージアプリの登録](https://learn.microsoft.com/windows/apps/develop/notifications/app-notifications/app-notifications-dotnet)を参照。

## 自動再接続

一時的な通信断では接続を作り直し、待ち時間を増やしながら再試行する。明示的な切断・アプリ終了で再試行を停止する。認証や設定が無効な場合は自動再試行を続けない。

AI実行、承認待ち、ユーザーごとの会話の紐付けを保持し、再接続で以前の依頼を再実行しない。切断中にサーバーへ送られた依頼を履歴から取り込まないため、必要な依頼は利用者が再投稿する。最初の接続案内を再接続のたびに投稿しない。

再接続の通信テスト4件で、MattermostとSlackの復帰、重複除外、進捗投稿IDの維持、不正認証とSocket Mode無効化時の停止を確認した。日本語の会話画面テスト13項目が成功し、待機依頼を残した復帰、接続案内の重複防止、同じ投稿の再送除外、復帰後の普通の返信も確認した。別PC・社内サーバーでの復帰は未検証。Slackはループバックの模擬Socket Modeでの試験であり、実ワークスペースでは操作していない。

## チャットからの停止・状態確認

- 開始済みスレッドでは `status` で本人の実行状態・待機件数を確認し、`stop` で本人の実行中の依頼と待機中の依頼を止める。明示的な呼び出しでは `!cab status` / `!cab stop` を使う。
- 対象は現在の接続先・プロバイダー・チャンネル・スレッド・送信者に一致する依頼だけ。他の許可ユーザーや別スレッドの依頼を表示・停止しない。
- 状態返信にはプロンプト、結果本文、ファイルパス、他人のセッション情報を含めない。操作のためにAIを呼び出さない。操作時と返信前に保存済みの許可設定を読み直す。
- 実行中の依頼を停止したときはCLIをキャンセルする。待機中の依頼は再実行せず終了表示にする。PC側で最初の実行確認を開いていた場合も、停止で確認を閉じる。

日本語の分離したポータブル画面で、本人の状態確認・別ユーザーと別スレッドの隔離、実行中と待機中の一括停止、古い回答コマンドがAI依頼にならないことを確認した。ループバックの模擬MattermostとオフラインCLIを使用し、実サーバーには投稿していない。コマンド解析の単体テスト16件も成功。
